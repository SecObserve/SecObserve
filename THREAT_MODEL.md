# Threat Model: SecObserve

## 1. System context

SecObserve (v1.53.0, BSD-3-Clause) is a self-hosted **vulnerability and license management platform**. It ingests output from many third-party security scanners (SAST / SCA / DAST / IaC / secrets) and SBOMs, normalizes them into a uniform `Observation` model, and lets product teams triage, risk-accept, and gate CI/CD on findings. It is **API-first**: a Python 3.12 / Django 6 / Django REST Framework backend served by Gunicorn (background jobs via huey), a TypeScript / React 19 SPA built on React-Admin and served by nginx, with MySQL or PostgreSQL for storage. The codebase is roughly 6,600 Python files (including tests and migrations) under `backend/application/` plus the SPA under `frontend/src/`.

It is deployed by dev/security teams either via the shipped Docker Compose files or the Helm chart, and is reached by three actor classes: (1) **CI/CD pipelines** uploading scan results with long-lived API tokens, (2) **interactive users** (per-product Reader→Owner roles, plus Internal / External / Superuser types) via a session JWT, and (3) **external IdPs** via OIDC. Authentication is dual: local username/password (Argon2) minting an HS256 JWT signed by a single DB-stored secret, or OIDC (Keycloak / Azure AD, auth-code + PKCE). Authorization is per-product RBAC (`Product_Member` / `Product_Authorization_Group_Member`), with OIDC group claims auto-mapped to authorization groups and an email regex deciding Internal vs External.

**Deployment context (this engagement, owner-stated):** the modeled instance is **exposed to the public internet** (behind operator-provided TLS), and is a **single-organization** deployment — but per-product access is treated as a real **need-to-know security boundary**: a user on Product A seeing Product B's observations is a breach, not just untidy. Code-verified role facts shape the actor model: the **Upload (role 2)** and **Writer (role 3)** roles both hold `Product_Import_Observations`, so scan-report upload is a relatively low-privilege, broad action; whereas integration configuration (`Api_Configuration_*`, issue-tracker fields via `Product_Edit`) and Rego rule authoring (`Product_Rule_Create`) are restricted to the more-trusted **Maintainer (4) / Owner (5)** roles (`authorization/services/roles_permissions.py`).

The product's defining security property is **multi-tenant confidentiality**: the database is a consolidated map of many products' *unpatched* vulnerabilities, so a cross-product read or an assessment-integrity flaw is high-impact. The primary untrusted-input surface is the scanner-report / SBOM import pipeline (~15 format parsers); secondary surfaces are server-side outbound integrations (notification webhooks, issue trackers, Dependency-Track) and the server-side Rego rule engine that mutates observation state.

## 5. Deprioritized

| threat | reason |
|---|---|
| Untrusted-deserialization RCE via pickle/yaml | jsonpickle is used encode-only (`unpicklable=False`); no `pickle.loads`/`yaml.load` on external input. The only `PickledObjectField` is the internal Constance config row, not fed by imports. Ruled out as a live RCE path. |
| SQL injection via raw queries | The only raw-SQL site is static DDL for a component view with no user interpolation; no `.raw()`/`.extra()`/`RawSQL`/f-string SQL on user input found. ORM-mediated throughout. |
| Spoofing of frontend origin / CSRF on the SPA | Token-based (Bearer JWT / API token) auth rather than cookie sessions for the API, mandatory `CORS_ALLOWED_ORIGINS`, and nginx CSP make classic CSRF/origin-spoofing low-likelihood. |
| Repudiation of read-only or low-value actions | Mutating assessment actions are already covered by the `Observation_Log` audit trail (folded into T8); standalone repudiation of read-only API calls is low value. |
| Network-layer / physical attacks on host and datastore | Out of scope for an application threat model — owned by the operator's deployment environment (the TLS-by-default gap is captured under T3 instead). |

## 6. Open questions

Owner-stated facts from this interview that affect a score and should be verified, plus what the code could not settle:

- [Owner-states] The instance is exposed to the public internet. **Affects:** T1/T2/T10/T16 likelihood (raised). **Verify by:** confirm ingress/firewall scope and whether the login + `UserAPIToken` endpoints are reachable from untrusted networks.
- [Owner-states] Cross-product access is a breach (need-to-know within a single org). **Affects:** T1/T11 impact (kept critical/high). **Verify by:** confirm with data owners whether per-product isolation is a compliance/contractual requirement.
- [Owner-states] The interviewed deployment overrides the shipped default secrets; the default-secret risk is a worry about *other* SecObserve installs. **Affects:** T3 status/scope (scored as an ecosystem/product footgun, not live here). **Verify by:** inspect this deployment's actual env injection (`SO_DJANGO_SECRET_KEY`, `FIELD_ENCRYPTION_KEY`, admin password) to confirm none equal the committed defaults.
- [Code-verified] Scan-report upload requires `Product_Import_Observations`, held by Upload(2)/Writer(3)+; integration config (`Api_Configuration_*`, issue-tracker via `Product_Edit`) and Rego authoring (`Product_Rule_Create`) require Maintainer(4)/Owner(5). **Affects:** T5 actor (low-priv) vs T6/T12/T17 actor (semi-trusted). - [Owner-states] The Rego rule-approval workflow (`assessments_need_approval`, `Product_Rule_Approval`) is not guaranteed to be enforced across SecObserve instances — it is optional / operator-dependent. **Affects:** T8/T12 status (now `unmitigated` at the product level; an instance that enforces approval mitigates both). **Verify by:** check per-product `assessments_need_approval` and rule-approval settings on a given deployment.
